The owner-approved simpler implementation, 2026-11-09

The visible screens remain the target and change only with the owner's approval. The mock itself, its data records and its fixtures are not frozen contracts. The owner approved these eight simplifications for the complete five-step build.

  1. Team area labels are optional, and generated team names remain unique. Repeated stages do not require a peer-area admission rule.
  2. A screen records routes only for the typed scenarios that it supports. Empty and partial binding lists are valid; unknown identities and duplicate bindings still refuse.
  3. Drafted fields use optional caller-reviewed comparison metadata. Missing review is Unavailable, and the engine does not parse an application schema from mock data. Actual artifact fingerprints and owner approval remain required.
  4. Pages read the existing typed engine records directly and reuse the shared request and recovery parts. No client data-transfer compatibility shapes or duplicate state machines are added.
  5. Browser checks group visible behaviors across 390, 768, 1440 and 2560 pixels in both color modes. They preserve authority, recovery and plain-text assertions rather than multiplying every fixture permutation.
  6. Shell use and harness sign-in share one real terminal service and emulator.
  7. Settings use one schema and loader with validated precedence. Installation and update use one installer path.
  8. Worker execution uses one transport behind the existing Runner, Git and terminal interfaces. The master retains the authoritative event log and duplicate-delivery protection.

The owner authorized step 2 before the aggregate step-1 gate. A page unit waits only for its own missing accepted dependency. W06, W07A and W10A ship as one composed foundation with individual author evidence, one builder full, and one fresh whole-composition review and full. Preview/editor display remains a separate owner decision in website-1/preview-editor-owner-decision.md. No policy or visible-screen change follows from a proposal alone.

Seat rules and integration

The harness is Codex on gpt-6.1-sol with high reasoning effort for builders and verifiers. The manager arranges Claude reviews separately. No Claude seat is started by this lead. The brief's builder-writes-tests instruction overrides the builder template's frozen-test assumption. Each verifier is fresh and did not build the unit. Each verifier reads the task, complete touched files, diff, relevant mock views and check suites. It runs the unit's tests and pnpm check in that worktree. A failed verification returns to the builder before a new verification round. The lead checks the signed commit and clean worktree, merges the branch, and runs pnpm check on that merge. No Co-Authored-By trailer is allowed. Every commit ends with Claude-Session: https://claude.ai/code/session_01TKETPLJ18SkHJufkrzj67J. The lead runs scripts/check-credits.sh. Every copied open-source file follows AGENTS.md and NOTICE.

Use tabs named web:<n>, split right, with at most three panes per tab. Use at most eight seats at once and keep system load below 38. Do not touch workspace w3 or pane w3:pAD. Read each active seat's session log used_percent. Keep every seat on Codex throughout, including after 90 and 97 percent. At 99 percent, tell the manager immediately so the owner can reset usage. Keep running seats going and resume new starts when the meter drops.

Stage gates and evidence

At the end of every numbered build step, the website team runs pnpm check and pnpm live-check:web. The manager runs pnpm live-check from the manager shell at the exact gate commit. The manager changed this execution assignment on 2026-11-08 after reproducing the baseline at 19 of 23 stages. Live account use is authorized by the brief. The sandbox-mcp failure recorded in issue 524 gets one rerun before regression classification. Reports name the commit checked and any dirty files. A running command remains pending until its exit code is collected. The plan does not claim that physical-phone or second-machine proof can be substituted by a browser resize or a same-host process. If that environment is unavailable, report the exact missing proof to the manager while continuing independent work.

The security invariant list is .scratch/security/attack-todo.md, under "From the website replacement". It describes what must hold and where, without attack recipes. Problems found while working are recorded in docs/issues.md in the same change. The manager allocates new issue numbers for defects found outside the unit being changed. An in-unit correction updates the unit's existing issue documentation and its result without allocating a separate issue number. New feature ideas go in docs/features.md. Do not reopen the owner's password, encryption, Unix-user, or single-user decisions.
