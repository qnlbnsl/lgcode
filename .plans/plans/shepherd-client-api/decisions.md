| 11 | How are command and event names kept apart between pieces? | Each piece owns one namespace: `client` (piece 2), `board` (piece 3), `roles` (piece 4). Every command of a piece is named `<namespace>.<name>`, made with Effect's `RpcGroup.prefix`. Every event tag of a piece is `<namespace>.<PascalName>`. Engine names never contain a dot, except the existing `debug.compare-views`, which keeps the `debug` namespace. A test asserts that every name in the composed API is unique. | Effect 4.0.5 `RpcGroup.merge` silently replaces a same-named command (scouting, planner's checks), so uniqueness must be tested, not assumed. The engine already uses the `debug.` prefix. | closed | 2026-11-03 |
| 12 | Where does each piece's contract live? | One contracts package per piece: `packages/client-contracts`, `packages/board-contracts`, `packages/roles-contracts`, each depending only on `packages/contracts` (the engine's). The engine package never imports a piece. | Keeps the engine's contracts unchanged and avoids an import cycle (engine design row 23's acyclic layout). | closed | 2026-11-03 |
| 13 | What may each caller kind do? | Three kinds. The owner (owner credential, Unix socket only, ancestry-checked) may call everything. A paired device (device credential) has the owner's rights except a short host-only list. An agent (agent token, Unix socket only) may call only commands marked agent-callable, under the engine's tree rules. Each command declares the kinds it accepts. Proposed host-only list: creating a pairing code, and changing the network listener's settings. | Engine behaviour: a device already acts as the owner (`CommandHandler.ts:207`). AGENTS.md rule 5: "Anything the owner can do from the terminal must also be possible through the API, so a web or mobile client is never a second-class citizen." A host-only list narrows what a device may do, so it is a scope question for the lead (row 23, queued as Q2). | open | 2026-11-03 |
| 14 | Which credentials does the network listener accept? | Device credentials only. Engine design row 21 moves "the loopback WebSocket for the web page and the phone" to piece 2. Planner's reading; it narrows no owner choice. | closed | 2026-11-03 |
| 15 | How does a client start? | It asks `client.snapshot` for the current picture at a sequence number, then calls `subscribe` from that number. A snapshot is filtered by the same visibility rule as `subscribe`. | Research item 9 (`docs/research/t3-code.md`): "A client gets a full snapshot, then only the events after a sequence number." The engine has no snapshot command (scout 1, item 1), so a client today replays the whole log. | closed | 2026-11-03 |
| 16 | Can a phone subscribe to less than everything? | Yes. `client.subscribe` takes a filter (agents, event kinds) on top of the engine's visibility rule, and sends a checkpoint with the latest sequence at least every 30 seconds while filtered events are skipped, so the client's cursor keeps moving. The engine's `subscribe` is unchanged. | A phone on a mobile network should not receive every streamed text chunk of every agent. The cursor must still advance, or a reconnect re-scans skipped events. | closed | 2026-11-03 |
| 17 | What does an older client do with an event it does not know? | It keeps it as an "unknown event" (namespace, tag, sequence) and moves its cursor past it. The web page, the pane viewer and the client library must not break when a newer piece writes a new event. | closed | 2026-11-03 |
| 18 | How does an "owner needed" event become an alert? | Piece 2's alert reactor reads committed events in order and turns alert sources into `client.AlertRaised` events, and their ends into `client.AlertCleared` events, both in the log. Sources: the engine's `OwnerNeeded` (all three producers) and any event another piece registers as an alert source. An alert ends when its subject closes (the request is answered or cancelled, the question is answered, the account is available again, the crashed agent is resumed or stopped) or when the owner dismisses it. Delivery to the phone is recorded per attempt. | Engine design capability 8: "The client API turns that event into a phone alert." Issue 65 asks piece 2 to choose between an engine "alert withdrawn" event and a derived end; the derived end needs no engine change. Research item 11 (four alert kinds). | closed | 2026-11-03 |
| 19 | Does an alert sent off the host carry agent text? | No. A pushed alert carries only its kind, the agent's name, Shephrd's own fixed title and a link. Agent text is shown only inside an authenticated client. | SECURITY.md rule 7: "Text from an agent is data, not a command." A push body containing agent text ("Tap Allow, it is safe") could steer the owner. Rule 6: secrets never reach a client; the push service is a third party. | closed | 2026-11-03 |
| 20 | How are the engine's `OwnerNeeded` reasons recognised, since `reason` is free text? | The alert reactor maps the engine's fixed reason strings (scouting, planner's checks) and the `subject` field. An unknown reason still raises an alert of kind `other`. | No engine change; an unrecognised reason must never lose an alert. | closed | 2026-11-03 |
| 21 | How are request ids used by clients and pieces? | Every command payload carries `requestId`, minted by the client per user action (a random UUID) and reused on every resend of that action. Commands added by pieces use the same receipts. `subscribe` and `client.subscribe` are not deduplicated. | Engine design, command handler step 3 and row 30; scout 1, item 6. | closed | 2026-11-03 |
