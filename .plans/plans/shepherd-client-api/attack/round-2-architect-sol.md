## Findings

### R2-A1. Live secret collection needs a writer boundary

**MAJOR. Category: Security (integrity), Design. Evidence: confirmed lifecycle gap. Responsible builder: unit 1b's engine builder, with unit 6b's alert builder.**

E27 fixes the startup deletion of the carrier token, but also starts using the collector during normal operation: the alert worker calls it after clearing a token (`contract.md:1818-1826`). The same edit preserves storing a secret before its reference commits (`contract.md:1828-1834`). It does not state which boundary protects the keep-set snapshot and deletion against secret-setting commands.

The existing collector obtains a keep set from `views.snapshot`, then calls `retainOnly` (`packages/engine/src/recovery/restart.ts:139-147`). Its service contract expressly assumes recovery runs it before commands can store anything (`packages/engine/src/commands/SecretStore.ts:13-15`). An account secret is stored at a fresh reference before its `AccountChanged` event is returned by the planner (`packages/engine/src/commands/accounts.ts:38-48`). The file semaphore serializes `put` and `retainOnly`, but `retainOnly` receives an already computed set; it does not serialize the views read with a command's publication (`packages/engine/src/accounts/SecretStore.ts:49-64`).

A permitted interleaving is:

1. Clearing a carrier token causes the worker to obtain keep set K.
2. An account secret command stores a fresh reference R, which is absent from K.
3. Collection acquires the secret-file permit and deletes R.
4. The account command commits its reference and reports success.

Collection after step 4 is equally unsafe if it still uses K. A newly re-entered carrier token has the same problem when a snapshot taken while the slot was unset is used after that slot is set again. The file semaphore does not prevent either order. Credentials must then be re-entered; the committed account or token-setting view cannot recover their values.

**Suggested fix:** make live collection an engine-owned operation that acquires the same writer permit used by secret-setting planners, reads the fresh published views, computes the keep set, and retains values before releasing that permit. `EventLog.transact` already holds its permit through publication (`packages/engine/src/log/EventLog.ts:242-266`), and command planning runs within that transaction (`packages/engine/src/commands/CommandHandler.ts:194-196`, `packages/engine/src/commands/CommandHandler.ts:260`). Specify the ordering explicitly and avoid recursively acquiring that permit inside an existing writer transaction. A targeted conditional deletion of the cleared slot is another option, provided its slot generation cannot delete a subsequent set. Keep this coordination in the engine helper so the client piece does not import the log writer, as E23 requires (`contract.md:1763-1765`). Add live interleaving coverage; E27's named restart test alone cannot establish it (`contract.md:1835-1839`).

### R2-A2. A previous success prevents the promised delivery after a carrier change

**MAJOR. Category: Design. Evidence: confirmed contradictory state rules. Responsible builder: units 6a and 6b.**

Pending requires that an alert have no `client.AlertDelivered` record (`contract.md:794-798`). Setting the carrier must make every open non-baseline alert pending once (`contract.md:818-819`; `plan.md:582`). Attempt results record a carrier name and attempt number, with no defined carrier configuration identity (`contract.md:754-756`).

For example, an approval alert is successfully sent to ntfy topic A and remains open. The owner changes to topic B on the same server. The old success still satisfies the first rule, so the alert cannot become pending under the second rule. A carrier name cannot distinguish those two destinations. An in-flight send to A that completes after the change has the same attribution problem: its success must not discharge B's promised send.

**Suggested fix:** define a delivery generation using the committed carrier-configuration event's sequence. Capture the generation with the destination before sending. Derive success, retry counts, and backoff for an alert within that generation, and record attempt outcomes against the captured generation. A completed send for an older generation must not settle the current one. This needs no credential in the log and no new queue. Alternatively, explicitly narrow the repending promise and define the resulting destination-change behavior in the contract and criterion 6.8. The current pair of rules cannot both hold.

### R2-A3. First-start scanning has no piece alert enumeration contract

**MAJOR. Category: Design. Evidence: confirmed missing shared interface. Responsible builder: unit 6a, with the board and roles builders.**

The round-one starting-position fold says a positioned reactor records the head, never replays history, and finds already open matters by a level scan (`contract.md:209-218`). Specifically, the alert reactor must raise baseline alerts for each open matter and never push those alerts (`contract.md:740-743`; `plan.md:590`).

Engine alert sources may read current views, but another piece's source remains a pure function of one envelope (`contract.md:674-685`). That source can raise or end an alert from an event. There is no corresponding function that enumerates a piece's open matters from its rebuilt view. The snapshot-section function is a different contract, with bounded summaries and possible truncation (`contract.md:419-434`, `contract.md:1359-1371`; `inputs/roles-plan.md:401-425`).

Consider an existing open owner-addressed board post when the alert reactor first starts. The raising event is below its new baseline position. Its source receives no historical envelope, so it cannot produce the required baseline alert. The board promises that alert through this interface (`inputs/board-contract.md:284-289`). Roles has the same issue for its open alert matters and explicit end events (`inputs/roles-plan.md:386-399`). This is reachable under the build order: board and roles can begin after unit 1b, without waiting for the alert reactor (`plan.md:397-398`). It also matters when adding this reactor to a populated log.

**Suggested fix:** add a narrow per-piece function over the full rebuilt views that enumerates open alert keys, kinds, agents, and subjects at the baseline's captured sequence. The alert reactor can use it alongside its engine level scan. Specify how a concurrent close is reconciled through the later stream. Require the board and roles to supply their entries. Keep the existing no-history-push policy. Do not use a truncated client snapshot as the source of truth. Extend the first-start acceptance case to include open and previously closed board and roles matters.

### R2-m1. The reserved device-id check names the wrong admission points

**MINOR. Category: Design. Evidence: confirmed code-anchor mismatch. Responsible builder: unit 1b.**

E12 says `open-web` is refused as a real device id in `mintDeviceCredential` and “DeviceAdded's planner” (`contract.md:1424-1426`). At the recorded commit, `mintDeviceCredential` accepts no arguments and returns only a token and its hash (`packages/engine/src/identity/devices.ts:12-15`). The handler's complete planner switch has no device-creation command (`packages/engine/src/commands/CommandHandler.ts:78-93`). `DeviceAdded` is an event schema, while device side rows are inserted directly by the writer (`packages/contracts/src/events.ts:177`; `packages/engine/src/log/EventLog.ts:202-204`).

The reservation is a clear intended rule, but these existing functions cannot enforce it as described, and a pairing planner is explicitly deferred (`contract.md:1006`). This is an anchor correction, not a claim that the unbuilt open-web path already admits forged devices.

**Suggested fix:** name the actual new validator or device-row admission check, state whether minting gains an id argument, and cover the existing side-row insertion path. Reject the reserved value for real-device records while continuing to permit it in the envelope's synthetic device field. The unit 1b test must not depend on the later pairing plan.

### R2-m2. An oversized global event has no thread from which to retrieve it

**MINOR. Category: Design. Evidence: confirmed retrieval-domain mismatch. Responsible builder: unit 3 and unit 2's client builder.**

Every `client.subscribe` event over 256 KiB becomes an oversized marker. The cursor advances, and the contract tells the client to fetch the whole event with `client.thread` (`contract.md:967-971`). That read accepts one agent's thread and must agree with the engine's thread membership (`contract.md:569-575`).

A `HarnessChanged` event can exceed the threshold: its settings contain uncapped string arrays such as `adapterArguments` and `models` (`packages/contracts/src/harnesses.ts:24-36`), and the event embeds those settings (`packages/contracts/src/events.ts:176`). A configuration between 256 KiB and the 1 MiB inbound cap can therefore produce this case (`contract.md:957-958`). Account, device, and harness events belong to no thread (`packages/engine/src/views/apply.ts:119-123`). An oversized harness event has no agent id to pass to the promised recovery read. The engine's unfiltered stream still exists, but no recovery rule chooses it, and it retains the slow-stream acknowledgement problem that motivated the marker.

**Suggested fix:** define a finite, visibility-checked way to retrieve a marked envelope by sequence, or state a separate global-event recovery rule and prove it covers every eligible tag. Add a global event to the real-frame oversized test. Keep the existing thread membership rule.

Those support the planned composition and the need to tolerate unknown values at that boundary. The [Socket API](https://effect.website/docs/v4/api/effect/socket/Socket) documents the global browser WebSocket constructor; future pairing still needs its own browser-compatible credential transport. This review does not assume a browser can attach Node-style arbitrary WebSocket headers.

The ntfy [publishing documentation](https://docs.ntfy.sh/publish/) documents sequence identities, replacement, and deletion. That supports the selected send/clear interface, while the declared real-server check remains necessary. Caddy's [reverse proxy defaults](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults) document its forwarding-header behavior. They do not establish the configuration of the owner's actual proxy. No claim is made that those deployment checks have already passed.
