### R4-A1. MAJOR. Adding the board events also requires changing the exhaustive lifecycle event table

Category: Design. Evidence status: confirmed source dependency omitted from the change inventory. Responsible builder: board contracts unit 1, coordinated with the client API engine-list unit.

Scenario: Unit 1 adds the eight board tags to `Event` as B2 prescribes. The existing lifecycle table is still typed over every tag of that union. Evidence: B2 lists `events.ts`, board event schemas and `visibility.ts`, and names only `events-roundtrip.test.ts` as an existing test to update (`board/plan.md:325`). The existing regression test discovers tags from `Event.members` at `packages/contracts/test/state-machine.test.ts:285` and calls `eventEffect` for every tag and lifecycle state at `packages/contracts/test/state-machine.test.ts:329`. This is a real additional reader of the widened union. The views' default branches do ignore unrelated tags, as B2 claims, but that does not remove this separate exhaustive dependency.

Suggested fix: Add the lifecycle table to B2 and its scope, and assign the corresponding shared E5 edit explicitly. Decide that each board tag keeps the lifecycle state, or specify any intended exception. Name `packages/contracts/test/state-machine.test.ts` as regression coverage. Its dynamic cases can keep their expectations if the selected behavior is `keep`; do not claim an existing test must be rewritten unnecessarily. Preserve exhaustive checking rather than casting around the missing entries. Record the decision and the responsible unit alongside B2.

This is a new omission in the direct-edit inventory. It is not a false claim that a check ran: this review did not build a future board implementation.

### R4-A2. MAJOR. The planner table does not define how board commands produce their transactional replies

Category: Design; Bug (failures). Evidence status: confirmed missing reply path in the specified engine edits. Responsible builder: client API engine-list unit and board command unit 3a, with the board handler tests.

Scenario: A caller opens a channel and needs its id, posts a question and needs its post id, or reads a page while marking its posts read. The board planners return the prescribed events, but the existing engine reply builder does not recognize those events. The new command can be selected and committed without producing the required result. An `afterCommit` response alone cannot supply the promised repeatable receipt result.

Evidence: The board puts six commands, including `board.read`, in the planner table (`board/plan.md:328`; `board/plan.md:556`; decision row 100 at `board/decisions.md:110`). The contract requires channel and post ids and read pages (`board/contract.md:435`; `board/contract.md:437`; `board/contract.md:439`). E3 replaces `supported` and the planner switch with a table, but defines no corresponding reply change (`inputs/client-api-contract.md:665`). E4 is expressly the other path, without a writer permit or receipt (`inputs/client-api-contract.md:679`).

At the recorded commit, `Plan` contains events, side rows and an optional `afterCommit`, with no transactional reply builder (`packages/engine/src/commands/internal.ts:41`). `replyFor` recognizes engine-specific events and command names only (`packages/engine/src/commands/CommandHandler.ts:97`). It is that function's reply that is passed to the receipt writer at `packages/engine/src/commands/CommandHandler.ts:269`. A repeat reads the stored reply instead of executing `afterCommit` (`packages/engine/src/commands/CommandHandler.ts:249`; `packages/engine/src/commands/CommandHandler.ts:255`). The late result overrides the response only on the initial call at `packages/engine/src/commands/CommandHandler.ts:278`.

There is a related contract choice for `board.read` that this missing reply path must settle. The board requires a receipt containing only its `board.Read` event (`board/contract.md:420`; criterion 5.11 at `board/plan.md:694`). The current generic writer stores both committed envelopes and the supplied reply (`packages/engine/src/log/EventLog.ts:210`). Saving a read page through that mechanism would also save its post text. Meanwhile the frozen API's paged-read rule says such reads are not deduplicated (`inputs/client-api-contract.md:179`; `inputs/client-api-contract.md:193`), while the board's planner registration and repeated-request criterion imply the transactional receipt path (`board/plan.md:684`).

Suggested fix: Specify one reply path for a planner entry, such as a reply function over the redacted committed batch, and make it part of the named engine edit. Use it for stable `board.open` and `board.post` ids. Separately decide how `board.read` returns a page and writes read acknowledgements while preserving the selected receipt policy. A transactional paged read without a stored page is a possible small solution, but its retry behavior and access recheck must be explicit. Reconcile E4 and the paged-read contract with that choice through the lead. Name the touched handler/log files and tests in the change inventory.

Keep the existing receipt expectations for engine commands. In particular, `packages/engine/test/commands/transaction-receipts.test.ts:33` requires an `accounts` or `harnesses` retry to return the first list after settings change. Add board-specific checks for the new reply and read policy. Do not globally replace stable mutation receipts with fresh reads.

This is not a re-file of the earlier receipt inventory finding. Listing receipt copies and scanning them for secrets remains correct. The newly specified direct engine path lacks the mechanism required to return the board's results and implement its narrower read-receipt promise.

### R4-A3. MAJOR. Refreshing condition summaries only after board events can leave the owner's wait held forever

Category: Design; Bug (timing). Evidence status: confirmed missing refresh trigger. Responsible builder: client wait-helper unit and board conditions/handler units, coordinated through the lead.

Scenario: A waits for a board answer. Its post closes, and its completion is queued. The owner's wait helper refreshes after the closing board events while the completion is still owed, so it records `holdsUnsettled(A) = true`. Delay the runner long enough to establish that observation. The completion is then accepted, A ends its turn, and no further board work occurs. The server's condition is now false and A is idle. The client's stored condition is still true. Under the prescribed refresh rule, nothing asks for the updated result, so the owner's wait never finishes although an engine wait can.

Evidence: The board clears completion debt on `DeliveryAccepted` (`board/plan.md:371`; `board/plan.md:457`). That is an engine event, not a board event. The helper reads results from the snapshot, then re-reads status summaries "after each board event" (`board/contract.md:366`; decision row 89 at `board/decisions.md:99`). Criterion 5.9 repeats that trigger restriction (`board/plan.md:692`). The API promises that the helper uses the same settled rule as the engine (`inputs/client-api-contract.md:419`).

The engine can produce this suffix without any board event: `accepted` returns `DeliveryAccepted` at `packages/engine/src/routing/deliveries.ts:104`; `turnEnded` returns `TurnEnded` and any engine pass-up events at `packages/engine/src/routing/deliveries.ts:92`. The delivery view changes to accepted at `packages/engine/src/views/apply.ts:281`, and the idle settled test checks that no queued or sent deliveries remain at `packages/engine/src/routing/waits.ts:39`. The board need not queue another wake after the last completion is discharged. The same event-family distinction matters to returned wakes, retry counts and stop-time debt cleanup.

Suggested fix: Define a complete invalidation rule for the bounded condition summaries. Refresh on every engine or board event that can change the board's condition inputs, or publish an explicit condition revision that the helper consumes. The smaller approach is to name those existing engine triggers and update the client helper. Specify how the helper waits for summaries at a sequence compatible with its lifecycle state before deciding to exit. Ignoring an older response prevents regression in time; it does not make a missing refresh happen. Assign the client change and a public helper test, rather than testing only the server's snapshot response.

Round 3 answer: Row 89 answers R3-A4/C3-04's incomplete-snapshot problem by sending computed results. It also supplies bounded status detail for group 3. Those representation fixes hold. The result cache now needs invalidation for the engine events that mutate the full view. This finding concerns the missing cross-piece update rule, not a request to download the full board view again. Row 90's narrowed silent-addressee policy remains correct.

### R4-A4. MAJOR. Bounding completion text still leaves its mandatory reply-id list unbounded

Category: Design; Bug (failures). Evidence status: confirmed missing cardinality rule under the literal completion contract. Responsible builder: board contracts and wake unit 3a, with the planner defining which replies the completion summarizes.

Scenario: An `all` question remains open while one addressee is paused. Another member posts repeated replies to it. Each is a valid same-channel `replyTo` post with `reply: none`. The first applicable answer resolves that addressee, but subsequent posts are not prohibited. They do not consume the author's open-question quota. When the remaining addressee finally resolves, the question can have more reply references than a completion can contain, even with all reply text omitted.

Evidence: A `replyTo` need only reference a post in the same channel whose caller is still a member (`board/contract.md:194`; `board/plan.md:466`). The planner writes `board.PostWritten` before its conditional first-resolution step (`board/plan.md:502`). The sixteen-item cap is for addressees, not replies, and the sixty-four cap is for open authored questions (`board/contract.md:192`; `board/contract.md:199`). Replies from other members are still permitted ordinary posts (`board/contract.md:254`). No clause defines a maximum number of replies per post or limits the completion to one selected answer per addressee.

Nevertheless the bounded completion must always contain "the ids of every reply" (`board/contract.md:248`), and criterion 3.13 covers just sixteen replies, one per addressee (`board/plan.md:550`). An in-memory illustrative encoding of 2,048 ordinary 36-character reply ids in a `replyIds` array occupied 79,886 bytes. That exceeds 65,536 bytes before any outcome, dispositions, markers or reply text. This is a size calculation, not an execution of future board schemas; the missing finite bound is independent of that particular encoding.

Suggested fix: Define a bounded set of decisive answers, for example at most one selected reply per addressee, if that is the intended meaning. Otherwise page reply references as well as reply text, with a count/cursor or post id in the completion. Keep every ordinary reply retrievable through `repliesTo`. State the completion acknowledgement semantics for that bounded form and add a repeated-reply case alongside the sixteen-large-replies test.

Round 3 answer: Row 88 fixes the demonstrated sixteen-large-text counterexample and several fitting completions in one wake. That part of group 2 holds. Its remaining promise to include every reply id does not have a corresponding reply-count bound. This is why the answer is insufficient for this different permitted input; it is not a request to restore full reply text to each completion.

### R4-A5. MINOR. The reducer's exhaustive ignore rule excludes the stop that must clear completion debt

The selected policy drops the debt, but the reducer's accepted event list ignores the stop, and no board event is named to record that removal. Deleting it only from live memory would not survive a rebuild.

Evidence: Criterion 2.1 says the reducer folds board events, `DeliveryAccepted`, `DeliveryReturned`, `AgentStarted` and `AgentGrouped`, and "ignores every other event" (`board/plan.md:457`). The stop-time removal is required at `board/plan.md:378` and `board/plan.md:593`, and decision row 95 explicitly closes round 3 logic m6 with that policy (`board/decisions.md:105`). The contract repeats it at `board/contract.md:247`. The current rebuild always applies the same pure fold from an empty view (`packages/engine/src/views/rebuild.ts:24`; `packages/engine/src/views/rebuild.ts:34`).

Suggested fix: Include `AgentStopped` in the board fold's input cases and make that fold clear the debt, or name the durable board event the reactor writes to do so. Add a stop-with-already-closed-debt case to the replay criteria. Keep crash debt survival as a control. This is minor because the product policy is already clearly decided; the exhaustive acceptance wording and its writer must agree with it. Row 95 is retained as policy, but its implementation contract is incomplete.
